## How the mechanisms work

**One evaluation.**
- Every `evaluation_interval_s`, at a fixed phase per monitor, the scheduler asks for the window
  that ends `evaluation_delay_s` before now.
- It reduces each group's points to one value (`avg(last_5m)` and the rest) and steps that group's
  state.
- If anything changed, it commits the new state, the events and the outbox rows in one SQLite
  transaction. Only after the commit does the dispatcher deliver.
- A crash therefore either loses the whole evaluation, which the next tick redoes, or keeps all of
  it. It cannot keep a notification without the state behind it. That is why restarting ozyd
  mid-alert sends nothing twice: the reloaded state is already ALERT, so the next step is not a
  transition.

**Hysteresis.**
- ALERT is entered past `critical` and left only past `critical_recovery`.
- A value swinging between the two stays put and notifies nothing.

**No data.**
- A group is absent when its window holds no points.
- It becomes NO_DATA once the newest point it ever had is `no_data_timeframe_m` older than the
  window's end.
- So the window must empty first: see Surprising.

**Backtest.**
- The same ticks (at the saved monitor's phase), window, reduction and state machine, run on a
  simulated clock over stored data.
- Two passes: the first collects events, and the second replays only the at most 20 groups it will
  draw.

## Trade-offs taken

- **State lives in SQLite (ADR-0048), not in memory.** It survives restarts and one transaction
  covers state, events and outbox, at the cost of a write per transition. No write happens on an
  unchanged evaluation.
- **Recipients come from the template source (ADR-0052).** They do not come from rendered text, so
  data cannot inject a mention, and conditional mentions are refused at save. Per-status routing
  took four review rounds of holes before it was dropped. It was not in the spec.
- **The UI draws only what the server answers.** The preview line is the per-tick evaluated value,
  the bands are the server's `levels`, and the markers are its transitions. There is no second,
  client-side reading of the grammar.
- **App-python monitors only (ADR-0053).** The app-node and app-ruby monitors in spec §5 name
  metrics nobody sends yet.

## How production systems differ

Prometheus evaluates rules inside the TSDB process and leaves notification to a separate
Alertmanager. Alertmanager owns grouping, inhibition and silences, and dedupes across HA replicas
by gossip. Here state, routing and delivery are one process with one SQLite file: fine on one box,
with no HA story at all.

Prometheus has a `for:` duration but no recovery threshold. Hysteresis there is written into the
expression, or not done. Its "no data" is `absent()`, written as a separate rule. Here no-data is
an option of every monitor, decided per group.

Loki's ruler is Prometheus rules over LogQL. Its log monitors count lines in a range, as these do.

## Surprising

- **No-data waits for the window to empty.** A heartbeat monitor on `max(last_5m)` with
  `no_data_timeframe_m: 3` went NO_DATA 5m16s after the worker stopped, twice in a row. The
  timeframe had passed long before the window stopped seeing the last beat.
  - The docs claimed "fires `no_data_timeframe_m` after the newest point". They now say it is the
    longer of the two.
  - `TestNoDataWaitsForTheWindowToEmpty` pins it.
  - With the shipped monitor on `last_2m`, it took 2m52s.
- **The first flood did nothing.** The app allows one submission in flight per user, so queue
  depth is about the number of users (arq counts running jobs too: 30 users read 31-33), and 5
  users can never back up a queue. The flood
  now holds 30 users' submissions queued.
  - Registering them is the slow part: the auth limit is 10 calls a minute per IP, and both
    register and login count.
- **Every worker start logs 4 "errors".** arq prints its banner before the app's startup hook
  installs the JSON formatter. The plain-text lines arrive on stderr, nothing parses a level from
  them, and the pipeline's stderr fallback marks them as errors.
  - The worker-errors monitor's threshold (> 5 in 5m) sits just above one restart, so two restarts
    in five minutes would page.
  - The fix belongs in the app: install the formatter at import. It is reported, not made here.
- **A laptop lid is an outage drill.** Clamshell sleep froze the Docker VM mid-evaluation for 15
  minutes. On wake, the evaluation finished with its own tick time, the transition was recorded at
  22:17:14, and the outbox delivered the recovery at 22:32:38: late, but not lost.
  - Meanwhile `/monitors/status` said healthy, because the watchdog only measures from inside the
    frozen process.
- **A window reduction reduces the expression, not the data.** My first 5xx monitor was
  `sum(last_5m):5xx/all*100 > 2`. On ten-second buckets that adds thirty percentages, so 1% errors
  read as 30 (and one failed request in a quiet bucket as 100). Its dry runs only ever showed 0, so
  nothing looked wrong; the review caught it, and a test that evaluates the shipped file now shows
  it. The same mistake made the latency monitor an unweighted mean of per-bucket p95s. Both now
  roll up so each bucket is whole. 5xx uses two-minute buckets and the max of the last three:
  rolled-up buckets are epoch-aligned, so a single five-minute bucket would split a burst across
  its boundary into two diluted halves, which round 2 of the review pointed out. Latency stays one
  five-minute sketch (ADR-0053).
- **I also had the 5xx ratio upside down.** I wrote it as the complement, so that a healthy app would
  read 0. docs/dashboards.md already says not to: the complement reads nothing when every request
  fails.

## What the review rounds taught

Two review rounds found 19 issues in this PR. Most were the same few mistakes, now rows in
AGENTS.md's pre-review table:

- **I checked queries only where they were healthy.** A dry run that reads 0 says the query parses,
  not that it fires correctly. Each monitor should be evaluated on data that should fire, should
  not, and sits on an edge.
- **I checked tag keys, not values.** `queue` was in the key list, and the backlog monitor merged
  two queues. `env` was in every list, and nothing was split by it. Listing values is how I found
  that log `env` is an attribute.
- **I skipped the docs.** `dashboards.md` already forbade the complement ratio.
- **My fixes changed the mechanism.** The round-1 rollup fixed a sum and introduced boundary
  splitting.
- **I fixed instances, not classes.** One recovery message was fixed, and three sibling monitors
  were left.

Before round 3, a self-review against those checks found three more without a reviewer: the env
merge, a log `.by("env")` that would have grouped everything under `(none)`, and an OOM grouping on
a label the sandboxes do not have.
