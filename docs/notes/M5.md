# M5 notes: tracing and APM

## What was built

- **Wire** (`pkg/wire/traces.go`): span types, per-span validation and normalization, `SampleKeep`,
  `NormalizePath`, `ParsePropagation`; shared vectors in `pkg/wire/testdata/traces/` that Go, Python
  and Node all load; goldens for hops B and F.
- **SDKs**: Python (`ozy.tracer`, `contextvars`) and Node (`AsyncLocalStorage`), the same shape: spans,
  a per-trace buffer flushed when the local root finishes, head sampling at the root, a bounded
  drop-oldest writer that never blocks the app. Integrations behind a public `Integration` interface:
  Python asgi (also the M3 metrics), sqlalchemy, redis, httpx, arq (the queue hop), logging; Node
  `withTelemetry`/`traceRoute`, sqlite, fetch, winston.
- **Agent**: `tracerecv` -> `concentrator` -> `sampler` -> forwarder. Statistics come first.
- **ozyd**: `POST /v1/traces`, `internal/tracestore` (Pebble), APM API.
- **UI**: service list and page, trace search with a duration scatter, trace view (canvas flame graph,
  waterfall, critical path, span detail, Logs tab, hatched queue wait), service map, log -> trace link.

## How the mechanisms work

**Context.** A span is "current" through a `ContextVar` / `AsyncLocalStorage`, so `await` and tasks
inherit it and a thread does not (Python needs `wrap_executor`). Across processes the context is three
headers or, through arq, a dict under `_ozymandias` in the job kwargs; the consumer `extract`s it and
starts a child, and the gap between `arq.enqueue` ending and `arq.job` starting is the queue wait
(also `queue.wait_ms`). `extract(inject(ctx)) == ctx` is a property; garbage in yields no context.

**Statistics before sampling.** The concentrator feeds each entry span (`_top_level`) into the ordinary
metric aggregator as a counter and a distribution sample stamped with the span's own end time, so
bucketing, zero-fill and DDSketch are the machinery metrics already had. The end-to-end test sends 200
requests with a 10% head rate and checks the service table says 200 requests and exactly 20 errors,
while the store holds a sample.

**Head sampling** is `(low64(trace_id) * 1111111111111111111 mod 2^64) < rate * 2^64`, a pure function
of the id, so every service agrees. `rate * 2^64` is exact in a double (a power-of-two scaling), so Python
`int`, Node `BigInt` and Go `uint64` agree bit for bit; 528 shared vectors check it.

**Key design.** See `docs/formats/tracestore-keys.md` and ADR-0045. Inverted time makes newest-first a
forward scan; a merge-operator counter makes the service map a read of a few keys.

## Trade-offs taken

- Entry spans only in the indexes. "Errors only" misses an error that arrives in a different request
  from its entry span (documented, not hidden).
- The service table has one row per (service, env, span name): percentiles of different operations cannot
  be merged, and sketches cannot be summed across names here.
- Metric tags are lower-cased, so the table shows `get /items/:id`; the trace `resource` filter ignores
  case so the link back works. (Found by the end-to-end test, not by thinking.)
- Edges are counted once per entry span (existence check on the entry key), so an agent resend does not
  double the map. The cost is one point read per cross-service entry span.
- Own propagation headers, W3C in M8 (ADR-0041). Explicit wrapping in Node (ADR-0043).

## How production systems differ

Datadog's agent does the same statistics-before-sampling (its "concentrator" is where the name comes
from) but with fixed 10s buckets keyed by more dimensions and stores sketches per bucket the same way.
Tempo stores traces in object storage by trace id with a bloom/index per block and has no secondary
indexes (search is TraceQL over blocks); this store's narrow Pebble indexes buy fast "latest N by
service" at the cost of write amplification and a retention sweep. Jaeger/Tempo service maps are
derived by a separate metrics-generator over *all* spans; here the map is from stored spans and
says so.

## Surprising

- The test that proved the statistics were exact also found that tag values cannot be quoted in
  metricql: the service filter I wrote with quotes matched nothing and returned an empty table, with
  no error. Absence, not failure.
- A writer test caught `full = False` left in the Python writer (the early flush at 100 chunks never
  fired). The test existed; the bug was a placeholder.
- Sketches and counts travel on separate hops, so a table can show requests before it has a p95.

## Measured

Apple-silicon laptop, quiet machine, single run each (references, not promises).

| What | Result |
|---|---|
| Agent trace path (decode, validate, stats via the real aggregator, samplers), 50 spans/request | ~335,000 spans/s, 1522 allocs/request |
| Store append, 4-span trace, no fsync | 46 us (about 87,000 spans/s) |
| Store append, fsync per request | 4.0 ms (so ozyd's batching matters, not span rate) |
| Latest 50 entries across 4 services (20,000 stored) | 53 us |
| Trace by id | 7.2 us |
| Python tracer, root span / child span | 3.7 us / 2.5 us (disabled 0.12 us) |
| Node tracer, single-span trace / per span in 10 | 0.88 us / 0.55 us (disabled 0.01 us) |

Unsampled costs the same as sampled by design: the trace is built and sent so the agent can count it.
