# M4 — Logs

## What was built

- **Agent tailers** (`internal/agent/tailer`): file tailer (poll, `(dev,inode)` identity, rotation, truncation,
  globs, start-position rules) and Docker tailer (logs API, frame demux, resume by timestamp, label opt-in),
  with a registry that commits a position only after ozyd accepted the lines.
- **Pipeline** (`internal/agent/logpipeline`): exclude → rate-limit → parse (json, grok built-ins, Rails request
  grouping) → remap → redact (last).
- **ozyd**: `POST /v1/logs` (store, then publish), the log store (`internal/logstore`: WAL, per-stream head, zstd
  blocks, chunk files, footer index, trigram bloom filters, retention), the live-tail hub (`internal/loghub`),
  and `/api/v1/logs`, `/aggregate`, `/facets`, `/tail` (SSE).
- **logql** (`internal/query/logql`): parser, planner split (labels → index, rest → scan), matcher, and `Needs`
  (what a block must contain, for the bloom skip).
- **Log Explorer** (`web/src/pages/logs`): query bar with completion, histogram, facets, virtual list, detail
  panel, live tail with pause, columns, saved views.
- **Python SDK** `JSONFormatter`; compose wiring (`deploy/agent.d/logs.yaml`, registry volume, `deploy/app-logs`).

## How it works

A line is read, grouped into an event (multiline), parsed and redacted, and posted in a batch. ozyd appends the
batch to the WAL (fsync = acknowledgement), then to each stream's head block, then publishes it to tails. A head
is sealed into a compressed block (plus its bloom filter) when it is big or old, one block per day so retention
can unlink whole files. A search takes the label index's streams, skips blocks whose bloom filter rules the
query's literals out, decompresses the rest and runs the same matcher the tail uses. DESIGN.md §14 and
`docs/diagrams/log-path.mmd` have the picture; `docs/formats/log-chunk.md` the bytes.

## Trade-offs taken

- **At-least-once, not exactly-once.** Duplicates (≤ one batch per crash) over any chance of a gap.
- **Polling, not inotify**, for files and containers: works over bind mounts and on every OS; costs up to a
  poll interval of latency.
- **Index-light store** (ADR-0039): five labels indexed, everything else scanned. Cheap writes and disk, search
  priced by bytes scanned.
- **Trigram bloom, not word bloom** (ADR-0040): a word filter cannot answer a substring search soundly.
- **Redaction on by default and last**: costs most of the agent's per-line time; a false positive hides a harmless
  value, a false negative leaks a secret.

## How the real systems differ

Loki indexes labels only too, but chunks are per-stream objects in object storage with a separate index and a
distributed read path; ours is one process and local files. Loki has no per-block bloom by default (newer
versions add structured-metadata blooms). Elasticsearch builds an inverted index over every term: search is fast
at any selectivity, writes and disk are several times costlier. Prometheus has no logs; Tempo is a trace store.

## Measured numbers

All on one laptop (Apple silicon, local disk), synthetic but realistic request logs.

| What | Result |
|---|---|
| Store append, no fsync | ~462k logs/s (500-log batches) |
| Store append, WAL fsync per batch | ~69k logs/s; ~7 ms per acknowledged batch |
| Agent pipeline, JSON line | ~3.5 µs/line (was ~14 µs: redaction was ~10 µs until each rule got a literal prefilter; see below) |
| logql parse | ~0.3 µs; compiled match ~0.16 µs per pair of logs |
| Hub publish to 32 tails (100 logs) | ~26 µs, 0 allocs |
| Compression | 60,000 logs, 10.7 MB raw → 1.45 MB (7.4x); optimistic, the corpus is repetitive |
| Bloom filters | +416 KB (22% of chunk files) |
| Rare word, 120 blocks | 1 read / 119 skipped: 78 ms → 0.8 ms (≈100x); absent word ≈500x |
| Common word, number compare, label | 0 skipped, no measurable cost |
| Live tail, file → agent → ozyd → SSE | 1.1 s (real compose stack, `make smoke`) |

The plan's L12 asked for 1 GiB of raw logs; this was measured on 10.7 MB and has **not** been scaled up.

## Surprises and bugs

- The plan's word-token bloom would have been unsound for substring search; hence trigrams and `logql.Needs`.
- Label opt-in for containers did nothing unless a docker *source* existed: unit tests built the tailer directly,
  only the live stack through the agent's own wiring showed it. Now an agent-level test and a smoke check.
- `logs.enabled` in `agent.yaml` blocked the compose fragment from setting it (a setting may be defined in one
  file); a test now loads the shipped files together.
- Redaction dominated the pipeline's cost (4x). Each default rule now has a cheap necessary-condition
  prefilter; a filter that wrongly says no leaks a secret, so the filtered redactor is checked against the
  unfiltered one over generated strings, and a line with any non-ASCII byte skips the filters (Unicode case
  folding: the Kelvin sign matches `k` in the rules' `(?i)`).
- Half the review findings in earlier milestones were regressions of fixes; every fix here got a mutation check.

## What is not done

- **L12 at 1 GiB**, and any measurement of search over a day's real volume.
- **L11 Playwright** (ADR-0035): the explorer has component tests, and no browser test; it was not opened in a
  browser against the live stack.
- app-node / app-ruby real onboarding (ADR-0037/0038): fixtures are synthetic.
- Docker events instead of container polling; sharing the M3 watcher.
- A Rails request open in the pipeline when the agent dies is lost.
- The trace link in the detail panel is inert until M5.
