## What was built

**PR 2: queued intake** (`pipeline.mode: queued`, [ADR-0056](../adr/0056-queued-intake-answers-on-durability.md),
DESIGN.md §17). Intake decodes, validates and checks the metric type, then `Produce`s the
validated request as JSON onto its signal's topic and answers `202`. One consumer per topic
(`RunConsumer`) polls, `Apply`s each record to its store, and commits the batch's last offset
only afterwards. A store error is retried with backoff; a record that does not decode is counted
and skipped. Lag, queue size and a broken-topic flag are self-metrics. `direct` stays, and stays
the default, until the smoke and e2e suites run queued.

How the pieces were checked, because the claim that matters is "queued answers like direct":

- The server's whole end-to-end suite (agent → ozyd → API) reruns with intake in front of the queue:
  `OZY_TEST_PIPELINE=queued`, `make test-queued`, a CI step. That is nine e2e tests, the log
  stress test and the rest of the package, all green in both modes. Three tests failed the first
  time (the two-engine round trip, the log self-metrics and the stress test), and every one posted and
  then read at once, which is exactly the thing queued mode changes.
- `TestIdempotent_RedeliveryLeavesStoresAsApplyingOnce` (rapid): a random record sequence, applied
  once and applied with random suffix replays, ends in the same TSDB samples and the same log
  search. Breaking the log store's dedupe fails it, with the doubled line in the message.
  It covers series and logs. Sketches and traces rely on the stores' own tests (last-write-wins and
  overwrite-by-key); they are not in this property.
- Mutation pass on the new intake/consumer code: nine mutants (one first failed to build and was rerun as compiling code), one survived at first
  (the backoff doubling) and now dies to a named test.

PR 1, for the record:

So far: `internal/queue` (PR 1, #67), a durable single-node queue. Each topic
is a directory of WAL segments holding offset- and time-stamped records.
Producers are acknowledged after a group-commit fsync. Consumers read below
the synced end and commit to an atomically replaced offset file. Retention
deletes whole segments below every consumer's commit. Format:
[queue-segment.md](../formats/queue-segment.md); decision:
[ADR-0055](../adr/0055-own-queue-not-kafka-or-nats.md).

## Measured numbers

### Group commit (PR 1)

```
go test ./internal/queue -run '^$' -bench Produce -benchtime 1s
```

macOS, Apple laptop SSD, Go's `File.Sync` is `F_FULLFSYNC` (about 4 ms per
call). 512-byte records; µs per record, wall clock, so with many producers
it is the inverse of throughput:

| sync window | 1 producer | 16 producers | 128 producers |
|---|---|---|---|
| none (`SyncInterval: -1`) | 3952 | 513 | 81 |
| 1 ms | 5009 | 321 | 48 |
| 5 ms (spec default) | 9302 | 611 | 74 |
| 20 ms | 24981 | 1581 | 198 |

What it shows: **the fsync is its own batching window.** With no window at
all, everything that arrives while one fsync runs goes out in the next one,
so 128 producers already share each fsync (81 µs per record against 3952 µs
alone). A deliberate window only helps when it is short next to the fsync
(1 ms: 48 µs). At 5 ms it is roughly a wash at 128 producers and a straight
cost below that, and 20 ms costs everywhere. A single producer always pays
fsync plus window.

These are laptop numbers. ozyd runs in a Linux VM under Colima, where fsync
is a different call on a different disk, and the default is decided there,
measured in PR 2 when the queue goes into the intake path.

### Group commit on Linux (PR 2)

Same benchmark in a `golang` container on the Colima VM (the platform ozyd runs on).
µs per record:

| sync window | 1 producer | 16 producers | 128 producers |
|---|---|---|---|
| none (`SyncInterval: -1`) | 568 | 493 | 355 |
| 1 ms | 2350 | 161 | **19** |
| 5 ms (the spec's) | 6757 | 430 | 55 |
| 20 ms | 23597 | 1503 | 194 |

The laptop's reading ("the fsync is its own window") does not hold here. A Linux fsync costs about
0.5 ms, so with no window the syncer wakes the moment one record is waiting and every fsync covers
only a handful. A 1 ms window collects more than it costs and wins by 19x at 128 producers; 5 ms
only adds latency. A lone producer pays 2.4 ms instead of 0.6 ms, which is nothing for an agent
that posts every ten seconds. Default changed to 1 ms (ADR-0056 §5). One run per cell on a shared VM:
the ordering is the finding, the exact numbers are not.

### Startup cost (PR 1)

Still to be measured: open time against topic size. Open reads every
retained record once (header only, no payload copy).

## Surprises and bugs

- **A mutant "killed" by an unrelated failure was a real race.** Removing
  the offset file's fsync made a concurrency test fail with "no such file".
  The cause was not the fsync: commits got faster, and that widened a window
  in retention, which unlinked a segment before updating the index. A
  consumer parked at the end of that segment saw it vanish while it was
  still listed. The lesson for mutation testing is to read *why* a mutant
  died. A kill from the wrong test is a lead.
- **Review round 1 (#67) found three ways to leave a topic that never opens
  again, or acks data that is not on disk:**
  - A consumer registering during a retention pass could start inside a
    segment being deleted.
  - A rollover's fsync failure was an ordinary, retryable error, which is
    the fsyncgate retry the design forbids.
  - Open trusted page-cache records as durable without syncing them.

- **Review round 2 moved the fsyncgate rule into the WAL, and round 3 took
  it back out.** Making every failed fsync final inside the WAL fixed the
  TSDB and the log store too. But nothing in ozyd yet reports a stopped
  store: `/readyz` comes in PR 6. A TSDB that had stopped would fail every
  write while every health check stayed green, which is worse than the retry
  it replaced. Now the WAL reports a failed fsync as `wal.ErrSync`, and each
  caller sets its own policy: the queue stops, and the TSDB and log store
  still retry. The WAL stops itself only when a rollover fails partway,
  because then it has no usable file at all. **Follow-up (PR 6):** stop the
  TSDB and log store on `ErrSync` once `/readyz` can say they have stopped.

## PR 3: shedding and the query limit

Built: shed thresholds in `intake.enqueue` (reads `Topic.Fullness`, one lock, no allocation), and
`httpserve.Limiter` wrapped around the mux for `GET /api/*` except `/tail`. ADR-0057. Checked with:
a table test over fullness 0.50/0.85/0.97 for each signal; the limiter's slots, queue, timeout and
exemption with a fake clock; a server test that an open live tail leaves the slot free. Mutants on the
thresholds, the queue bound, slot release and the tail exemption all die; two of them first "died" by
a go test timeout, which is not a kill, so the limiter tests now carry their own deadlines.
Not measured: how the limit changes dashboard load time, and ingest throughput with queries at the
limit (L12). The isolation the spec asks for is by bounds rather than separate pools: see ADR-0057.

## PR 4: the agent's disk buffer

Built `internal/agent/spool`: a single-consumer FIFO per endpoint on the WAL framing, drop-oldest by
whole segment, a cursor replaced atomically without an fsync (ADR-0058, format in
[agent-buffer.md](../formats/agent-buffer.md)). The forwarder moves its oldest memory payloads to the
spool on overflow and the rest at shutdown, reads the spool's head before newer payloads of the same
endpoint, and drains series, then sketches, then spans. Logs are not in it: they never queued in the
agent, the file is their buffer, so "a full buffer pauses tailing" was already true by construction.
Checked with: a model test (any put/deliver/restart interleaving delivers the put sequence once, in
order), a fuzz target over arbitrary segment bytes, damage found at open and while running, a torn tail,
a bad cursor, a failed fsync, and forwarder tests for overflow without loss and in order, restart
survival, the drain order, the cap, and an unusable directory. Seven mutants on the spool and five on the
forwarder integration all die; the spool's fsync and its damage-while-running branch first survived and
now have tests.
Startup scan (`go test -bench BenchmarkOpen ./internal/agent/spool`, 130 MB in 16 segments, macOS, warm
page cache): 34 ms, 3.9 GB/s. That is the CPU cost of reading and checksumming; a cold disk is bounded by
its read speed instead, so a full 512 MiB spool on a 500 MB/s disk is about a second per endpoint, and
the three endpoints open one after another before the agent serves anything.

Review round 1 and 2 found, among others: a failed fsync that left an unindexed record the next write made
reachable (the spool now stops, like the queue); a payload spilled while its request was in flight and then
delivered anyway; and, in my own fix for that, a wake-up lost because the send loop read the clock twice
(the second read could land past the retry time, making the wait zero). The flake showed up as 2 of 4
repeated runs failing with nothing delivered, which is why the buffer's tests are run in a loop.

Not done: a crash test that kills the agent process (L5 for the buffer), spill and replay throughput, the
three-times-the-cap total on disk, and a test for the spool being unreadable from the send loop's side
(the retry timer, `diskRetry`).

## Follow-ups

- **Log redelivery after a seal is stored twice.** The dedupe remembers the stream's head, and a
  block seal empties it. A batch applied, sealed and then redelivered (crash between the seal and the
  commit) shows its lines twice; `TestAppend_RedeliveryAfterSealIsNotRecognized` pins it. The M7
  criterion "kill -9 ×50, no visible duplicates" is **not shown for logs** until this closes: either
  carry a per-stream key set across seals and restarts, or pass the queue offset to the store as an
  idempotency token. Decide before PR 7's chaos drills.
- Queued mode, not yet measured: end-to-end latency (statsd packet to queryable) against direct, and
  max sustained ingest per signal (spec L12). Not yet built: a crash-loop test of the consumer (L5),
  and the sketches/traces cases of the redelivery property.
- Live tail repeats a line after a redelivery (the hub tracks no offsets). Acceptable, but say so in
  the UI docs when tail is next touched.

- TSDB and log store: treat a failed fsync as final (fsyncgate), with
  `/readyz` reporting it. PR 6.
- `queue`: the index's handling of a rollover followed by a failed write into
  the new segment is not pinned by a test. It needs a fault-injecting
  filesystem that fails one write after an open; L5 work later in M7.

## PR 5: keys, a login, and per-key limits

**What was built.** `internal/auth` (keyring, token buckets, the gate, the key API), the
`api_keys` table, a login form in the UI, and the agent sending `X-Ozy-Key`. ADR-0059 holds
the decisions; the short version: a key is 256 random bits stored as a SHA-256, one admin
password gives a session cookie, everything under `/api` is closed unless a path is named
public, and with `auth.enabled: false` (the default) none of it exists.

**How it works.** The gate wraps the whole mux, outside the query limiter, so a caller with no
credential cannot take a query slot. An ingest request is authenticated by hashing the header
and comparing against every stored hash in constant time, then charged one request and its
bytes against the key's buckets; spans and log bytes are charged inside the handlers, after
decoding, from the principal the gate put in the request context. A refusal is `429` with a
whole-second `Retry-After`, or `401`; both are counted under `ozy.intake.rejected{reason}`.

**Bugs found by looking before review** (the classes in AGENTS.md §3):

- *Silent emptiness.* The mux names the route on the request copy it was handed, and the request
  counter reads the original, so every authenticated request would have been filed under
  `route:unmatched`. Found by reading `Instrument`, fixed by copying the pattern back, pinned by
  `TestAuth_RequestsAreCountedUnderTheirRoute`, and confirmed against a real `ozyd` and agent
  (20 accepted requests under `POST /v1/series`, rejections under `auth-reject`).
- *A decision in the wrong layer.* Throttling wrong passwords by "N failures, then lock" lets an
  attacker lock the owner out. It is a one-at-a-time gate with a delay and a bounded wait
  instead, and a test shows 40 parallel guesses are 429'd past the bound while the owner still gets in.
- *A claim nothing tests.* "A refused body does not cost a request token" and "an undeclared length
  is charged as the largest body" each survived the first mutation pass and now have a test that
  kills the mutant. The `ozy_` prefix check in `Authenticate` still survives: it is an early exit
  and the hash comparison would reject the same keys, so it is equivalent, kept for the work it saves.
- *Environment names.* `OZY_API_KEY` would have made ozyd warn at startup about a variable that
  "matches no setting", because `OZY_` is the override prefix. The variables are
  `OZYMANDIAS_ADMIN_PASSWORD` and `OZYMANDIAS_API_KEY`.
- *Data loss on a misconfigured key.* The forwarder gave up on any 4xx, so a missing or wrong key
  would have dropped everything collected until it was fixed. `401` is now retried with a counter.

**Review round 1** (ten findings, nine fixed, one claim corrected):

- A bearer password reached admin routes with no throttle, and the public session probe answered for
  it: the login gate guarded nothing. All password guesses now share one gate, and the probe answers for
  the cookie only. Mine to have seen: the gate was built for the form and the second door was added after.
- ADR-0059 said login was "never locked out" under a flood. It is not: new logins get 429 while the
  flood lasts. The claim is corrected and a test pins what does hold (held sessions are unaffected).
- Logout was classified admin, so a stale cookie got 401 and was never cleared. A sibling bug in the
  same table: the UI's own endpoints. Fixed with a test.
- A synchronous SQLite write (the `last_used_at` touch) sat on the intake path behind the metadata
  writer lock. Now a goroutine, once a minute per key.
- A spans or log-byte refusal kept the request and byte tokens the gate had taken, so a retrying sender
  tripped the other limits and the rejection reasons hid the cause. Refunded now, with tests on both.
- The log sink treated 401 like any failure (no counter), and a key from a file with a trailing newline
  was an invalid header that looked like a network error. Both fixed.
- The UI only noticed a 401 from a query; mutations (Save) and a cut-off live tail did not reach the
  login form. Both do now.
- Zero could not mean "unlimited" once a default existed: a negative limit now does.
- The keyring scanned every key ever made; it is a map by hash now.

**Review round 2** (ten findings; six fixed, one corrected in docs, three answered):

- Fixed: a failed start (the unset password path) leaked every store it had opened; the keyring's
  `last_used_at` goroutine had no owner, so `Keyring.Close` now waits for it and the server calls it before
  closing the database; `touch` took a global write lock on every request, now a per-key atomic with a
  compare-and-swap; a store or queue failure, or a shed, kept the request's charge (the first round's refund
  only covered two of the ways a request is refused), so the gate now gives back everything a request spent
  when it ends in 429 or 5xx; key creation answered 400 for our own failures and echoed the database's
  error text; the `Principal` doc claimed nil-safety that `Allow` did not have.
- A sibling found by the same reading: the query limiter's cancelled-waiter answer (499) was filed under
  `route:unmatched`, the very bug its 503 branch already avoided. Fixed and pinned.
- Corrected, not fixed: a flood of wrong bearer passwords also makes correct bearer requests wait or 429
  (the previous round fixed the oracle, and made this reachable). The ADR now says so and tells scripts to log in once.
- Answered: `ozy.consumer.{logs,spans}_rejected` are documented in the catalog as reserved and zero today
  (logs and spans are validated at intake); that was a decision in PR 2, not this change. Queued-mode log
  head dedupe dropping genuinely identical lines in separate batches is the documented trade-off in
  ADR-0056 and DESIGN §17, with its post-seal gap pinned by a test; neither is touched by this PR.

**Mutation pass.** 15 mutants of the gate, limits and keyring. On the first run 9 were killed by a
failing assertion, 3 were build failures (an unused variable), 1 was "killed" only by a test timeout
(a `defer` that deadlocked) and 2 survived. The build failures were rerun as code that compiles and
died by assertion; the timeout one was rerun by changing the queue size instead, and a test
killed it; one survivor (the unknown-length charge) got a test and died. The other survivor, the
`ozy_` prefix check, is equivalent (above). Three mutants of the UI gate and its probe: two died, one
(`!res.ok`) survived until a test sent a session-shaped body with a 502.

**Not done.** Per-key series limits, total active series and the tag allow/deny list (PR 5b, see
ADR-0059: they need the key in the queued record). Coverage of the UI gate is unit-level; there is
no browser test of a real login. Login throttling is unmeasured under real concurrency. How much a
key check costs with many keys is not measured (it is linear in the number of keys).
