## What was built

**PR 2: queued intake** (`pipeline.mode: queued`, [ADR-0056](../adr/0056-queued-intake-answers-on-durability.md),
DESIGN.md §17). Intake decodes, validates and checks the metric type, then `Produce`s the
validated request as JSON onto its signal's topic and answers `202`. One consumer per topic
(`RunConsumer`) polls, `Apply`s each record to its store, and commits the batch's last offset
only afterwards. A store error is retried with backoff; a record that does not decode is counted
and skipped. Lag, queue size and a broken-topic flag are self-metrics. `direct` stays, and stays
the default, until the smoke and e2e suites run queued.

How the pieces were checked, because the claim that matters is "queued answers like direct":

- The server's whole end-to-end suite (agent → ozyd → API) reruns with intake in front of the queue:
  `OZY_TEST_PIPELINE=queued`, `make test-queued`, a CI step. That is nine e2e tests, the log
  stress test and the rest of the package, all green in both modes. Three tests failed the first
  time (the two-engine round trip, the log self-metrics and the stress test), and every one posted and
  then read at once, which is exactly the thing queued mode changes.
- `TestIdempotent_RedeliveryLeavesStoresAsApplyingOnce` (rapid): a random record sequence, applied
  once and applied with random suffix replays, ends in the same TSDB samples and the same log
  search. Breaking the log store's dedupe fails it, with the doubled line in the message.
  It covers series and logs. Sketches and traces rely on the stores' own tests (last-write-wins and
  overwrite-by-key); they are not in this property.
- Mutation pass on the new intake/consumer code: nine mutants (one first failed to build and was rerun as compiling code), one survived at first
  (the backoff doubling) and now dies to a named test.

PR 1, for the record:

So far: `internal/queue` (PR 1, #67), a durable single-node queue. Each topic
is a directory of WAL segments holding offset- and time-stamped records.
Producers are acknowledged after a group-commit fsync. Consumers read below
the synced end and commit to an atomically replaced offset file. Retention
deletes whole segments below every consumer's commit. Format:
[queue-segment.md](../formats/queue-segment.md); decision:
[ADR-0055](../adr/0055-own-queue-not-kafka-or-nats.md).

## Measured numbers

### Group commit (PR 1)

```
go test ./internal/queue -run '^$' -bench Produce -benchtime 1s
```

macOS, Apple laptop SSD, Go's `File.Sync` is `F_FULLFSYNC` (about 4 ms per
call). 512-byte records; µs per record, wall clock, so with many producers
it is the inverse of throughput:

| sync window | 1 producer | 16 producers | 128 producers |
|---|---|---|---|
| none (`SyncInterval: -1`) | 3952 | 513 | 81 |
| 1 ms | 5009 | 321 | 48 |
| 5 ms (spec default) | 9302 | 611 | 74 |
| 20 ms | 24981 | 1581 | 198 |

What it shows: **the fsync is its own batching window.** With no window at
all, everything that arrives while one fsync runs goes out in the next one,
so 128 producers already share each fsync (81 µs per record against 3952 µs
alone). A deliberate window only helps when it is short next to the fsync
(1 ms: 48 µs). At 5 ms it is roughly a wash at 128 producers and a straight
cost below that, and 20 ms costs everywhere. A single producer always pays
fsync plus window.

These are laptop numbers. ozyd runs in a Linux VM under Colima, where fsync
is a different call on a different disk, and the default is decided there,
measured in PR 2 when the queue goes into the intake path.

### Group commit on Linux (PR 2)

Same benchmark in a `golang` container on the Colima VM (the platform ozyd runs on).
µs per record:

| sync window | 1 producer | 16 producers | 128 producers |
|---|---|---|---|
| none (`SyncInterval: -1`) | 568 | 493 | 355 |
| 1 ms | 2350 | 161 | **19** |
| 5 ms (the spec's) | 6757 | 430 | 55 |
| 20 ms | 23597 | 1503 | 194 |

The laptop's reading ("the fsync is its own window") does not hold here. A Linux fsync costs about
0.5 ms, so with no window the syncer wakes the moment one record is waiting and every fsync covers
only a handful. A 1 ms window collects more than it costs and wins by 19x at 128 producers; 5 ms
only adds latency. A lone producer pays 2.4 ms instead of 0.6 ms, which is nothing for an agent
that posts every ten seconds. Default changed to 1 ms (ADR-0056 §5). One run per cell on a shared VM:
the ordering is the finding, the exact numbers are not.

## Surprises and bugs

- **A mutant "killed" by an unrelated failure was a real race.** Removing
  the offset file's fsync made a concurrency test fail with "no such file".
  The cause was not the fsync: commits got faster, and that widened a window
  in retention, which unlinked a segment before updating the index. A
  consumer parked at the end of that segment saw it vanish while it was
  still listed. The lesson for mutation testing is to read *why* a mutant
  died. A kill from the wrong test is a lead.
- **Review round 1 (#67) found three ways to leave a topic that never opens
  again, or acks data that is not on disk:**
  - A consumer registering during a retention pass could start inside a
    segment being deleted.
  - A rollover's fsync failure was an ordinary, retryable error, which is
    the fsyncgate retry the design forbids.
  - Open trusted page-cache records as durable without syncing them.

- **Review round 2 moved the fsyncgate rule into the WAL, and round 3 took
  it back out.** Making every failed fsync final inside the WAL fixed the
  TSDB and the log store too. But nothing in ozyd yet reports a stopped
  store: `/readyz` comes in PR 6. A TSDB that had stopped would fail every
  write while every health check stayed green, which is worse than the retry
  it replaced. Now the WAL reports a failed fsync as `wal.ErrSync`, and each
  caller sets its own policy: the queue stops, and the TSDB and log store
  still retry. The WAL stops itself only when a rollover fails partway,
  because then it has no usable file at all. **Follow-up (PR 6):** stop the
  TSDB and log store on `ErrSync` once `/readyz` can say they have stopped.

## PR 3: shedding and the query limit

Built: shed thresholds in `intake.enqueue` (reads `Topic.Fullness`, one lock, no allocation), and
`httpserve.Limiter` wrapped around the mux for `GET /api/*` except `/tail`. ADR-0057. Checked with:
a table test over fullness 0.50/0.85/0.97 for each signal; the limiter's slots, queue, timeout and
exemption with a fake clock; a server test that an open live tail leaves the slot free. Mutants on the
thresholds, the queue bound, slot release and the tail exemption all die; two of them first "died" by
a go test timeout, which is not a kill, so the limiter tests now carry their own deadlines.
Not measured: how the limit changes dashboard load time, and ingest throughput with queries at the
limit (L12). The isolation the spec asks for is by bounds rather than separate pools: see ADR-0057.

## Follow-ups

- **Log redelivery after a seal is stored twice.** The dedupe remembers the stream's head, and a
  block seal empties it. A batch applied, sealed and then redelivered (crash between the seal and the
  commit) shows its lines twice; `TestAppend_RedeliveryAfterSealIsNotRecognized` pins it. The M7
  criterion "kill -9 ×50, no visible duplicates" is **not shown for logs** until this closes: either
  carry a per-stream key set across seals and restarts, or pass the queue offset to the store as an
  idempotency token. Decide before PR 7's chaos drills.
- `internal/api/apm.go` builds a service row from three separate p50/p95/p99 sketch queries, so the API
  can briefly answer p95 with no p50 (the flake behind #68). Fix with one merged sketch read per entry
  name and a deterministic `internal/api` test with a staged `SketchReader`.
- Queued mode, not yet measured: end-to-end latency (statsd packet to queryable) against direct, and
  max sustained ingest per signal (spec L12). Not yet built: a crash-loop test of the consumer (L5),
  and the sketches/traces cases of the redelivery property.
- Live tail repeats a line after a redelivery (the hub tracks no offsets). Acceptable, but say so in
  the UI docs when tail is next touched.

- TSDB and log store: treat a failed fsync as final (fsyncgate), with
  `/readyz` reporting it. PR 6.
- `queue`: the index's handling of a rollover followed by a failed write into
  the new segment is not pinned by a test. It needs a fault-injecting
  filesystem that fails one write after an open; L5 work later in M7.
