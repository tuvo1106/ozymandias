## How it works

### One request, end to end

Follow one request from an app to a chart. Write side: the middleware's
[`__call__`](../../sdk/python/src/ozy/integrations/asgi.py#L128) times the request and
[`_record`](../../sdk/python/src/ozy/integrations/asgi.py#L176) tags it with the matched
route pattern from [`_route_pattern`](../../sdk/python/src/ozy/integrations/asgi.py#L191),
then sends a counter and a distribution over UDP. The agent buckets them every 10 s and the
TSDB stores them (DESIGN.md §9–11).

Read side, for `sum:http.request.count{service:api} by {route}.as_rate()`:

1. [`Parse`](../../internal/query/metricql/parse.go#L30) builds the AST, positions kept.
2. A dashboard calls [`Batch`](../../internal/query/metricql/eval/batch.go#L88), a single
   widget [`Eval`](../../internal/query/metricql/eval/eval.go#L211); both go through the same code.
3. [`plan`](../../internal/query/metricql/eval/plan.go#L59) fixes the grid and the default
   rollup for the metric's type.
4. [`node`](../../internal/query/metricql/eval/eval.go#L350) dispatches; for a query,
   [`query`](../../internal/query/metricql/eval/query.go#L13) builds the
   [`selector`](../../internal/query/metricql/eval/query.go#L91), looks the selection up under its
   [`selectionKey`](../../internal/query/metricql/eval/batch.go#L210), and on a miss
   [`bucketize`](../../internal/query/metricql/eval/query.go#L236)s each series onto the grid.
5. [`groupOf`](../../internal/query/metricql/eval/query.go#L280) and the
   [accumulator](../../internal/query/metricql/eval/query.go#L304) space-aggregate by `route`.
6. [`applyModifiers`](../../internal/query/metricql/eval/modifier.go#L15) divides by the bucket
   width for `as_rate()`; a binary operator's [`join`](../../internal/query/metricql/eval/arith.go#L36)
   matches groups on identical tags.

### The query pipeline

A query reads left to right as the pipeline that answers it: select series, time-aggregate
into buckets, space-aggregate by group, modify (`as_rate`), then fill, functions and
arithmetic. The order is the point. Taking each series's per-bucket max and then
summing across series is not the max of the summed series, and a percentile merged
from sketches is not the average of percentiles. That last fact is enforced rather than documented: `avg:` on a distribution
is an error that names `p50`…`p99` instead.

Two decisions shaped the evaluator more than the grammar did:

- **One grid per request (ADR-0016).** Every node in a request lands on one bucket grid,
  and sources of the interval that disagree are an error. Without that, `a / b` joins two
  series on different grids and means nothing.
- **Shared selection in a batch (ADR-0018).** A dashboard is one request. Half of a node,
  select and reduce onto the grid, depends only on the selector, grid and rollup method, so it
  is memoised for the batch and dies with it. Nothing is shared between requests, so nothing is
  stale.

### Collectors

The agent gains a scheduler that runs collectors on an interval. Host, Docker and the five
checks are all collectors.

- **Rates are per-second gauges (ADR-0026).** A gauge averages over a bucket, and the average
  of per-second values over a bucket is the bucket's rate at any width, so no collector has to
  guess the dashboard's interval.
- **Docker stats are one-shot (ADR-0030).** Read with `one-shot=true`; CPU % is computed
  between the previous run's sample and this one, so its window is the 15 s collection
  interval and a container's first run has no CPU value.
- **Short-lived containers.** A judge sandbox lives for under a second, so polling `stats`
  would never see it. The event stream does: exits and lifetimes become `container.exits` and
  `container.lifetime`.
- **A restarted agent writes no bucket its predecessor did (ADR-0029).** See Surprises.
- **Autodiscovery by label.** `ozy.check.<check>.<setting>` labels on a container become
  check instances, added to and removed from the running scheduler.

### The app side

The Python SDK's `MetricsMiddleware` is pure ASGI (not `BaseHTTPMiddleware`) and tags requests
with the matched route *pattern*, never the raw path, so `/problems/{slug}` is one series
however many slugs exist. The app talks to the SDK through one file, `app/telemetry.py`, which
is the only importer of `ozy`, and does nothing when `OZY_AGENT_HOST` is unset.

## Key concepts learned

- **Aggregation order is part of the meaning.** Time-aggregate, then space-aggregate, and a
  percentile is merged from sketches, never averaged. Most "wrong number" questions on a
  dashboard are a question about which stage a step ran in.
- **No series is not zero.** An empty selection is no line, not a line of zeros, and no modifier
  changes that. `a / b` with an empty `a` draws nothing. The complement (`100 - non-5xx / total`) draws 0
  for a healthy service but draws nothing when every request is a 5xx, so it is the wrong fix
  for an error-rate chart (`docs/dashboards.md`). I shipped it once and a review caught that.
- **A tag is a series.** Cardinality is decided where a value enters: a route pattern instead of
  a raw path, a whitelist for a method. The place to discipline it is the code that emits the tag.
- **Measure the live thing.** Container short lives, restart overlap, cron deduplication across
  workers: none of these showed up in a unit test, and each took one live run to find.
- **A fix is code too.** Half the review findings were regressions from the previous fix; the
  habit that helps is listing the callers before editing shared code.

## Trade-offs taken

- **No arithmetic between distributions (ADR-0019).** `dist:` has its own endpoint and refuses
  to appear in an expression. Silently using the left operand would be worse than refusing.
- **A missing `by` key is grouped under its absence.** The plan said `"N/A"`; the code
  leaves the key off the group's tags, and `query-language.md` and a test say so. ADR-0034
  records it (after the fact) and the plan is amended.
- **Dashboards are baked into the ozyd image.** Shipping one means a rebuild;
  `shipped_test.go` validates every shipped dashboard in CI.
- **Tags are bounded sets, in code.** The middleware's `method` tag is a whitelist plus
  `OTHER`, the route is the pattern or `unmatched`, and a Stripe event type outside the known
  set folds to `other`. A tag is a series.
- **The app is wired through one seam**, so removing the integration is deleting one file and
  its call sites, and the vendored wheel keeps the app's Docker build self-contained.

## How the real systems differ

- **Prometheus** pulls, so its `rate()` runs over a range vector of raw samples and handles
  counter resets at query time. Here the agent pushes already-aggregated 10 s buckets, so
  `as_rate()` divides a bucket's sum by the interval and the counter-reset problem moves to the
  scrape side (the openmetrics check). Its `histogram_quantile` interpolates linearly inside
  fixed buckets; ours does too, and the sketch path (DDSketch) gives a relative-error bound
  instead of a bucket-width one. Having both on the same data is the comparison the milestone
  wanted. It has not been run on a real app (app-ruby is the planned source).
- **Datadog** is the model for the query shape (`agg:metric{filter} by {tag}`), for autodiscovery
  by container label and for the one-agent-per-host layout. Its backend is unseen here; ours is a
  single-node TSDB.

**Query latency (L12, `BenchmarkQueryLatency`).** The evaluator answering `sum:req.count{service:api}
by {route}.as_rate()` over an in-memory store, one point per series per 10 s, 180 buckets, 10 groups.
Medians of 4 runs of `-benchtime 5x`, 10 cores, Time Machine running (so the large cells are noisy):

| window | 10 series | 100 series | 1000 series |
|---|---|---|---|
| 1 h | 0.064 ms | 0.37 ms | 1.9 ms |
| 1 d | 0.21 ms | 2.1 ms | 23 ms |
| 7 d | 1.9 ms | 21 ms | 256 ms (241–297) |

Command: `go test -run '^$' -bench QueryLatency -benchmem -benchtime 5x ./internal/query/metricql/eval/`.
Reading it: time grows with the points read, about 2.4–3.4 ns per point from 1 d to 7 d (the 1 h
cells are dominated by fixed costs), rising to 4.2 ns at 7 d × 1000, where the ~1 GB working set no longer fits in cache. Allocation
per query is independent of the window (3.8 MB for 1000 series at every window): memory scales with
series, not points. The slowest cell, 7 d × 1000, is the per-node series limit over a week, and
answers in about a quarter of a second. This is the evaluator only; reading sealed blocks from the
TSDB is not in it. (An earlier version of the benchmark reported 150 ms for that cell; it varied the
bucket count with the window and was a single run.)

Cardinality of the integrated app (`/api/v1/metrics/cardinality`), after a normal session
that included submissions in two languages: the app's metric families peak at **18 series**
(`http.request.count`; this includes an earlier run of the same app under its previous service
name), against the 500 limit. Separately, `container.exits` and
`container.lifetime.*` sit at 258 series because throwaway containers with random names
(the Docker VM's own) each mint one. Not an app metric, but it is the closest thing to the
limit and it grows with container churn: a value from outside becoming a label. It has no
issue and no ADR yet, and is under "What is not done".

Tests: the shikomi backend suite with telemetry inert (`OZY_AGENT_HOST` unset): **563 passed,
94.03% coverage** against its 80% gate. The Python SDK suite: 166 passed. The last full
`make ci`, on the #38 branch before its final review round: Go 94.3%, SDK 97.69%, web 511 tests.

## Surprises and bugs

- **Review rounds were mostly my own previous fix.** The Docker collector (#35) and the checks (#36)
  each took 8 `/code-review` rounds. About half of each round's majors were regressions from the
  round before: a clash rename that hit the built-in Docker collector; "built-in" inferred from an
  empty `Keep` slice, wrong for a lone check; a URL fix that broke URLs with a password. The rule
  that came out of it: before committing a fix to shared code, list its callers and test the ones
  you did not mean to change, and decide by what a thing *is*, never by a proxy.
- **A restarted agent rewrote its predecessor's bucket** and the TSDB rejected it as out of order,
  visible only because the judge's churn (~80 exits per 20 s) made it happen constantly. Fix: a
  floor under every bucket an agent may stamp (ADR-0029).
- **The RESP parser's 19-digit overflow panic survived seven review rounds.** The fuzz test
  existed; its seed corpus had no boundary numbers and CI fuzzes for 10 s. Seed parsers with
  max/overflowing values and run `make fuzz-long` before the first review.
- **The VM clock stepped.** The Colima VM's clock can sit hours behind the Mac after sleep and
  then step, so a smoke test that used `date` flaked. Smoke windows use the server's own clock.
- **`host` had 24 values** on ozyd's own metrics because every `make up` gave the container a new
  hostname. Found by the cardinality page the milestone built; fixed with a stable compose
  `hostname:` (ADR-0025).
- **A blank widget said "No data".** No test caught it; a browser check did. Every finding in the
  dashboard viewer's review (#28) was a widget concluding a fact from a missing value.
- **§4, found only against the live stack:** FastAPI's `include_router(prefix=)` is not in the
  route pattern, and a Starlette `Mount` reports no route at all in some versions, so those routes
  tag as `unmatched`; arq runs a cron job once per scheduled time across *all* workers, keyed by
  name, so two workers registering `heartbeat` meant the judge worker's never ran, with no error
  anywhere; sandboxes started through the Docker API carry no compose labels, so a dashboard filter
  on `compose_project` emptied exactly the chart for them; and a dashboard that named the real app
  in a public repo had to become template variables.
- **The plan's own examples were stale.** Example 1 (`avg:http.request.duration`) is an error by a
  later decision. Example 3 groups by a tag the integrated app does not emit.

The bug classes above, and the checks that would have found each earlier, are in
[AGENTS.md §3](../../AGENTS.md) ("Before you ask for a review").
